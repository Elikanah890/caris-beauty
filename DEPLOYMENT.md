# Deployment — VPS (recommended) + optional Render/Vercel

Production target: **one VPS running Nginx + PostgreSQL + the Node API + the Next.js PWA over HTTPS**. The Render/Vercel instructions lower in this file remain valid as an alternative.

---

## 0. VPS — Nginx + Node + HTTPS

PWA installation and offline mode require **HTTPS**. Use a domain such as
`shop.example.com` and a Let's Encrypt certificate.

### Build and run the frontend

The browser calls the API through the same origin, so `NEXT_PUBLIC_API_URL` can be
relative. Server-rendered public catalog pages use `API_INTERNAL_URL` to reach the
backend directly.

```bash
cd frontend
npm ci
NEXT_PUBLIC_API_URL=/api/v1 \
API_INTERNAL_URL=http://127.0.0.1:4000/api/v1 \
npm run build

# systemd/PM2 should run this, not an interactive shell:
NEXT_PUBLIC_API_URL=/api/v1 \
API_INTERNAL_URL=http://127.0.0.1:4000/api/v1 \
npm start
```

`NEXT_PUBLIC_API_URL` is baked into the browser bundle at **build time**. Rebuild
the frontend after changing it. `npm start` listens on `127.0.0.1:3000`.

### Build and run the backend

```bash
cd backend
npm ci
npm run build
npm run migrate

NODE_ENV=production \
HOST=127.0.0.1 \
PORT=4000 \
COOKIE_SECURE=true \
CORS_ORIGIN=https://shop.example.com \
DATABASE_URL=postgresql://... \
JWT_ACCESS_SECRET=... \
JWT_REFRESH_SECRET=... \
npm start
```

Run both processes under systemd or PM2 so they restart after reboot.

### Nginx

Copy [`deploy/nginx-caris.conf.example`](./deploy/nginx-caris.conf.example) to
`/etc/nginx/sites-available/caris`, replace the domain and certificate paths,
then enable it:

```bash
sudo ln -s /etc/nginx/sites-available/caris /etc/nginx/sites-enabled/caris
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d shop.example.com
```

The example config:

- proxies `/` to Next.js on `127.0.0.1:3000`
- proxies `/api/` to the Express API on `127.0.0.1:4000`
- serves `/sw.js` and `/manifest.json` with revalidation headers
- caches hashed `/_next/static/` assets immutably
- enables HSTS, gzip and forwarded headers

### PWA verification on the VPS

1. Open `https://shop.example.com` once online.
2. DevTools → **Application** → **Manifest**: confirm `start_url` is `/pos`, the
   192/512 icons load, and there are no manifest errors.
3. **Application** → **Service Workers**: confirm `/sw.js` is activated and
   controlled by the page.
4. **Network** → set **Offline**, reload, and confirm the app shell or `/offline`
   opens.
5. Sign in once online so the offline password credential is cached, go offline,
   sign in with the same password, open POS, and make a local sale.
6. Reconnect and confirm the queued sale syncs.

The service worker is generated by `npm run build`. Never edit or commit
`public/sw.js`; it is gitignored and regenerated on every build.

## Managed Postgres with Neon

Neon is a good fit when you do not want to run PostgreSQL on the VPS itself.
The API and migrations enable SSL automatically for `*.neon.tech` hosts, and
also honour `sslmode` when it is present.

1. Create a project at [neon.tech](https://neon.tech) and open **Connect**.
2. Copy a connection string. For a single long-running VPS the direct
   (non-pooled) host is fine; both direct and `-pooler` hosts work:

   ```env
   DATABASE_URL=postgresql://user:password@ep-example-123456.us-east-2.aws.neon.tech/neondb?sslmode=require
   ```

3. Put it in `backend/.env` locally, or in the backend service environment on
   the VPS. Never commit it.
4. Run the migrations once:

   ```bash
   cd backend
   npm ci
   npm run migrate
   ```

5. Start the API as usual. The connection uses SSL because the host is
   `*.neon.tech`; you do not need any extra SSL flags in the code.

### Notes

- Keep `sslmode=require` in the URL for clarity. The app strips it before
  handing the URL to `pg` (which would otherwise warn about future semantics)
  and configures SSL itself.
- On networks with broken IPv6 routing, the backend prefers IPv4 so Neon's
  AAAA records cannot make connections hang. IPv6 is still used when no IPv4
  address exists.
- `TEST_DATABASE_URL` should stay on a local PostgreSQL instance; backend tests
  drop and recreate the `public` schema, so never point it at Neon.

## 2. Render — database + API

The repo contains [`render.yaml`](./render.yaml). In Render:

1. **New → Blueprint**
2. Connect the GitHub repo.
3. Render creates:
   - PostgreSQL database `caris-db`
   - Web service `caris-api`

If you prefer manual setup:

### PostgreSQL
- Create a PostgreSQL instance.
- Copy its **internal connection string**.

### Web service
- Root directory: `backend`
- Build command:
  ```bash
  npm ci --include=dev && npm run build
  ```
- Start command:
  ```bash
  npm start
  ```
- Health check path: `/api/v1/health`

### Backend environment variables

| Variable | Value |
|---|---|
| `NODE_ENV` | `production` |
| `HOST` | `0.0.0.0` |
| `PORT` | Render provides it automatically |
| `DATABASE_URL` | PostgreSQL internal connection string |
| `JWT_ACCESS_SECRET` | random 48+ chars |
| `JWT_REFRESH_SECRET` | different random 48+ chars |
| `ACCESS_TOKEN_TTL` | `8h` |
| `REFRESH_TOKEN_TTL` | `30d` |
| `CORS_ORIGIN` | your Vercel URL, e.g. `https://caris-beauty.vercel.app` |
| `COOKIE_SECURE` | `true` |

`CORS_ORIGIN` supports multiple origins separated by commas.

### Migrations

`render.yaml` runs migrations automatically with:

```bash
node dist/src/db/migrate.js
```

If you set up the service manually, open the Render **Shell** and run:

```bash
node dist/src/db/migrate.js
```

(or `cd backend && node dist/src/db/migrate.js` if the shell starts at the repo root).

## 3. Vercel — frontend PWA

1. **Add New → Project** → import the same GitHub repo.
2. Set **Root Directory** to `frontend`.
3. Framework preset: **Next.js**.
4. Build command: `npm run build`.
5. Environment variable:

| Variable | Value |
|---|---|
| `NEXT_PUBLIC_API_URL` | `https://<your-render-service>.onrender.com/api/v1` |

No trailing slash.

`NEXT_PUBLIC_API_URL` is baked in at build time — changing it requires a **redeploy**.

---

## 4. Connect Vercel back to Render

After Vercel gives you the production URL:

1. Go to Render → `caris-api` → Environment.
2. Set:
   ```env
   CORS_ORIGIN=https://your-vercel-app.vercel.app
   ```
3. Save and redeploy the backend.

If you use a custom domain, add it to `CORS_ORIGIN` too.

## 5. First run on a fresh database

The database starts empty (only reference units are seeded by migrations).

1. Open:
   ```
   https://your-vercel-app.vercel.app/auth/setup
   ```
2. Create the shop name, owner account and receipt prefix.
3. You are signed in as the owner.
4. Add products, categories and staff.

The API refuses a second setup, so this page is safe after the shop is configured.

## 6. PWA / HTTPS

PWA install and the service worker require **HTTPS** (Vercel and Render provide it).

After deploy:

- **Android Chrome:** menu → *Install app*, or the in-app **Install** button.
- **iPhone/iPad Safari:** Share → *Add to Home Screen*.
- **Desktop Chrome/Edge:** install icon in the address bar or the in-app button.

The service worker is generated by `npm run build` on Vercel. `public/sw.js` is intentionally gitignored.

### Service worker cache header (required behind a proxy)

`/sw.js` must not be cached by Nginx or the browser. The VPS example config in
`deploy/nginx-caris.conf.example` already does this. At minimum:

```nginx
location = /sw.js {
  proxy_hide_header Cache-Control;
  add_header Cache-Control "no-cache, no-store, must-revalidate" always;
  add_header Service-Worker-Allowed "/" always;
}
```

`/manifest.json` should also use `Cache-Control: public, max-age=0, must-revalidate`.

## Troubleshooting

**Login works but refresh/logout fails**
- `COOKIE_SECURE` must be `true` on Render, and the backend must be on HTTPS.
- `CORS_ORIGIN` must exactly match the frontend origin.

**“This device was signed out”**
- The device was revoked from Profile → **Your devices**, or it was reassigned to another account. Sign in again with the account password.

**PWA install button does not appear on desktop**
- Chrome only fires the install prompt after its PWA criteria are met. Check the address-bar install icon, or use the app’s **Install** button after visiting online once.

**Offline page instead of app**
- Open the app online once so the shell caches, then go offline.
- In `next dev`, the service worker is intentionally disabled; test offline with a production build.
